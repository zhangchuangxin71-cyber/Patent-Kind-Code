# 大模型语义信息生成与实验参与详细说明

生成日期：2026-09-05

本文专门说明本项目中的语义信息怎样得到、DeepSeek 和 SBERT 分别做了什么、语义向量怎样进入推荐模型，以及实验结果究竟能够证明哪一部分有效。内容以实际代码、缓存、日志、最终 `semantic_prior.pt` 元数据和 corrected-v3/v4 实验记录为准。

## 1. 先给出准确结论

本项目中的“大模型参与”不是让大模型直接推荐物品，也不是让大模型读取用户测试答案。实际流程分为两层：

1. **DeepSeek `deepseek-chat`：可选的离线文本整理器。**它逐个读取物品的公开文本元数据，将冗长、格式不统一的标题、类别、描述和属性压缩成不超过约 80 个英文词的语义摘要。
2. **Sentence-BERT：固定的本地语义编码器。**项目使用 `sentence-transformers/all-MiniLM-L6-v2`，把原始文本或 DeepSeek 摘要编码成 384 维向量。

生成的向量保存到本地 `semantic_prior.pt`。后续训练、验证和 OOD 测试只读取这个本地文件，不再调用 DeepSeek API，也不需要大模型在线推理。

完整数据流为：

```text
物品公开元数据 items.jsonl
        │
        ├─ 标题、前20个类别、描述、前10个属性，最多512字符
        │
        ├─ 可选：DeepSeek 离线摘要（Food / Yelp / KuaiRec 使用）
        │          └─ 写入可恢复的 llm_rewrite.jsonl 缓存
        │
        └─ SBERT all-MiniLM-L6-v2 本地编码并归一化
                   │
                   └─ semantic_prior.pt：每个物品一个384维语义向量
                                      │
                   ┌──────────────────┴─────────────────┐
                   │                                    │
          corrected-v3 E3                       corrected-v4 主实验
       条件门控 + InfoNCE                    用户画像 + 分数级 late fusion
```

## 2. 哪些数据集真正调用了 DeepSeek

最终 `.pt` 文件中保存了 `mode`、`backend`、编码器、物品数、维度和覆盖率。实际情况如下：

| 数据集 | DeepSeek 是否参与 | 送入 SBERT 的文本 | 最终编码器 | 物品数 | 最终覆盖率 |
|---|---|---|---|---:|---:|
| Food | 是 | DeepSeek 摘要 | all-MiniLM-L6-v2 | 6309 | 100% |
| Yelp2018 | 是 | DeepSeek 摘要；3 个 API 失败项回退为原始文本 | all-MiniLM-L6-v2 | 12185 | 100% |
| KuaiRec v1 | 是 | DeepSeek 摘要 | all-MiniLM-L6-v2 | 10612 | 100% |
| KuaiRec v2 exposure | 是，复用 v1 先验 | 直接复制 v1 的 DeepSeek+SBERT 先验，因为两版使用相同物品映射 | all-MiniLM-L6-v2 | 10612 | 100% |
| MovieLens-1M | 否 | 原始电影标题与类别等元数据 | all-MiniLM-L6-v2 | 2380 | 100% |
| Amazon Beauty | 否 | 原始商品元数据 | all-MiniLM-L6-v2 | 6086 | 100% |

因此，“所有实验都由 DeepSeek 生成语义”是不准确的。准确说法是：**所有正式语义实验都使用 SBERT 语义向量；其中 Food、Yelp2018 和 KuaiRec 的文本先经过 DeepSeek 离线摘要，MovieLens-1M 和 Amazon Beauty 直接编码原始元数据。**

## 3. DeepSeek 接收的原始信息是什么

语义生成脚本先按 `item_id` 排序物品，保证第 $i$ 行文本、缓存和最终第 $i$ 行向量与同一个物品对应。

对每个物品，代码按以下顺序拼接文本：

1. `title`：物品标题；
2. `categories`：最多取前 20 个类别，写成 `categories: ...`；
3. `description`：物品描述；
4. `attributes`：最多取前 10 个键值对，写成 `attributes: key=value; ...`；
5. 各部分用 ` | ` 连接；
6. 最终最多保留 512 个字符。

只有当物品满足 `text_available=true` 且拼接文本非空时，才把该物品标记为可用语义。没有文本的物品不会让大模型虚构描述；其向量会被置零，并由 `semantic_mask=false` 屏蔽。

这意味着 DeepSeek 看到的是**物品侧静态公开元数据**，不包含：

- 用户 ID 或用户画像；
- 用户的 train、validation 或 test 交互序列；
- OOD 测试正样本；
- 推荐指标或模型预测；
- 其他用户的行为信息。

## 4. DeepSeek 的调用方式

代码使用 OpenAI 兼容客户端访问 DeepSeek：

- 模型：`deepseek-chat`；
- API 地址：`https://api.deepseek.com`；
- 调用粒度：每个有文本的物品一次请求；
- `temperature=0.2`：降低随机性，使摘要更稳定；
- `max_tokens=160`：限制输出长度；
- 请求间隔：默认 0.05 秒；
- API 密钥仅从环境变量 `DEEPSEEK_API_KEY` 读取，不写入数据、缓存或实验报告。

实际提示词为：

```text
Summarize the following item for recommendation semantic matching.
Keep key attributes, categories, and intent in one short English paragraph
(<=80 words). No marketing fluff.

<拼接后的物品文本>
```

提示词要求模型完成的是“面向推荐语义匹配的摘要”，并明确：

- 保留关键属性；
- 保留类别；
- 保留物品意图或用途；
- 形成一个短英文段落；
- 不超过约 80 词；
- 去掉营销性和无信息量内容。

这里没有要求 DeepSeek 打分、预测点击率、生成标签或推荐列表。DeepSeek 的输出只是更紧凑、格式更统一的文本中间件。

## 5. 实际文本改写示例

以下样例来自项目现有公开数据和缓存，展示 DeepSeek 的真实作用。

### 5.1 Food

原始信息包含菜名、大量标签、描述和配料：

```text
sauteed fennel | categories: 15-minutes-or-less, time-to-make, ... |
this recipe came from the foodtv.com kitchens ['olive oil', 'garlic',
'fennel', 'kosher salt', 'fresh ground black pepper', 'water']
```

DeepSeek 缓存摘要：

```text
Sautéed fennel is a quick, easy side dish or lunch, ready in 15 minutes.
It features fennel, olive oil, and garlic, seasoned with salt and pepper.
This low-calorie, low-protein, low-sodium, and low-cholesterol recipe suits
North American, European, or South American cuisines for seasonal occasions.
```

作用：把分散的标签、配料和用途整理成连贯语义，减少纯标签堆叠。

### 5.2 Yelp2018

原始信息包含店名、城市、类别和大量结构化属性：

```text
Gio Taco | categories: Restaurants, Mexican | Tucson, AZ |
attributes: Ambience=...; RestaurantsGoodForGroups=True; BikeParking=True; ...
```

DeepSeek 缓存摘要：

```text
Gio Taco is a Mexican restaurant in Tucson, AZ. It offers outdoor seating,
full bar, bike parking, and is wheelchair accessible. Good for groups, kids,
and dogs. No reservations. Price range moderate.
```

作用：把嵌套、截断或布尔形式的属性转成语义编码器更容易处理的自然语言。

### 5.3 KuaiRec

原始信息是中文短视频标题和类别编号：

```text
精神小伙路难走 程哥你狗粮慢点撒 | categories: 8 |
精神小伙路难走 程哥你狗粮慢点撒
```

DeepSeek 缓存摘要将其解释为具有幽默、情感关系和娱乐意图的短视频内容。作用是把短标题中的网络表达补充为相对规范的语义描述，再交给英文 SBERT 编码。

需要注意：这种解释可能带入大模型的概括偏差，因此项目使用 shuffled semantic 对照验证“正确物品—语义对应关系”是否有用，但尚未做人工逐条事实核验。

## 6. 缓存、断点续跑和失败回退

DeepSeek 输出不是直接留在内存后丢弃，而是逐条追加到：

```text
data_strict/processed/<dataset>/v1_strict/cache/llm_rewrite.jsonl
```

每行格式为：

```json
{"i": 物品排序位置, "text": "DeepSeek摘要或回退文本"}
```

缓存机制有四个目的：

1. 中断后可以从已完成物品继续；
2. 同一批摘要只需调用一次 API；
3. 后续把 hash 编码替换为 SBERT 时，可复用完全相同的摘要；
4. 推荐训练与评测不依赖网络或外部大模型服务。

当前缓存记录数：Food 6309、Yelp2018 12185、KuaiRec 10612，与三个数据集的物品数一致。

如果单次 DeepSeek 请求失败，代码不会删除物品或产生空向量，而是使用该物品的原始拼接文本作为回退结果，并把回退文本写入缓存。现有日志显示：

- Food：正式全量改写没有记录 API 失败；
- KuaiRec：正式全量改写没有记录 API 失败；
- Yelp2018：物品位置 2982、2983、2984 曾发生连接错误，三项回退为原始文本；
- 最终三套先验的语义覆盖率仍为 100%。

## 7. SBERT 如何把文本变成语义向量

DeepSeek 输出仍然是字符串，推荐模型不能直接对字符串做点积。因此项目用本地 Sentence-BERT 进行数值化：

```python
model = SentenceTransformer(
    "sentence-transformers/all-MiniLM-L6-v2"
)
item_emb = model.encode(
    texts,
    batch_size=64,
    normalize_embeddings=True,
)
```

对于每个物品 $i$，SBERT 输出 384 维向量 $e_i\in\mathbb{R}^{384}$，并进行 L2 归一化：

\[
\lVert e_i\rVert_2=1.
\]

语义相近的文本通常会得到方向更接近的向量，后续可用向量点积计算余弦相似度。SBERT 在本项目中不做微调，权重固定；其作用是“文本到稠密向量的编码器”，不是在线聊天模型。

最终文件 `semantic_prior.pt` 包含：

```text
item_emb:      [n_item, 384] float32，每个物品的语义向量
semantic_mask: [n_item] bool，表示该物品是否有有效文本
meta:          数据集、mode、backend、模型名、物品数、维度、覆盖率
```

## 8. 早期 hash 先验与最终先验的区别

项目早期在尚未安装 `sentence-transformers` 时，曾把 DeepSeek 摘要送入确定性 hash-bag 编码器，得到同样为 384 维但语义能力较弱的向量。hash 方法只是把词映射到固定随机表后求和，不是真正的语义模型。

2026-07-24 安装 Sentence-Transformers 后，项目重新读取已经完成的全量 DeepSeek 缓存，并用 `all-MiniLM-L6-v2` 重建 Food、Yelp2018 和 KuaiRec 的 `semantic_prior.pt`。日志显示三套最终文件均为：

```text
mode=llm, backend=sbert, emb_dim=384, coverage=1.0
```

因此正式实验使用的是 **DeepSeek 摘要 + SBERT**，不是早期 hash 版本。hash 结果只能作为开发历史或编码质量诊断，不能冒充终版实验。

## 9. 语义信息在 corrected-v3 E3 中怎样参与训练

corrected-v3 的正式 E3 主要把物品语义作为扩散模型的条件信息，并加入语义对齐损失；其正式配置不是 corrected-v4 所使用的冻结 checkpoint 分数级 late fusion。代码后来也支持通过 `semantic_score_alpha` 打开额外分数路径，但该参数默认是 0，专利主表中的分数级证据应归入 corrected-v4。

### 9.1 条件门控融合

设环境/因果表示为 $z_c$，SBERT 物品语义为 $z_s$。因为 $z_s$ 是 384 维而当前因果隐空间通常为 8 维，先通过线性层将语义投影到相同维度，再计算门控：

\[
g=\sigma\left(\operatorname{MLP}([P_c(z_c);P_s(z_s)])\right),
\]

\[
z=g\cdot P_c(z_c)+(1-g)\cdot P_s(z_s).
\]

其中 $g\in[0,1]$：

- $g$ 越大，保留的因果/协同表示越多；
- $1-g$ 越大，语义先验权重越大。

语义 mask 只对物品节点打开。用户节点和无文本物品保持原因果表示，不把不存在的语义强行注入。

融合后的 $z$ 作为扩散去噪模型的条件输入。此处使用的是预先保存的向量，不调用 DeepSeek。

### 9.2 InfoNCE 语义对齐

E3 还让模型预测的物品表示靠近同一物品的语义表示，并远离批内其他物品语义：

\[
L_{sem}=-\frac{1}{B}\sum_i
\log\frac{\exp(\operatorname{sim}(c_i,s_i)/\tau)}
{\sum_j\exp(\operatorname{sim}(c_i,s_j)/\tau)}.
\]

实际设置：

- 温度 `τ=0.07`；
- 每次最多抽样 512 个具有文本的物品；
- 正样本是同一物品的模型表示与语义表示；
- 其他物品作为批内负样本；
- E3 正式设置通常为 `lambda_sem=0.1`；
- E4 将 `lambda_sem=0`，用于隔离 InfoNCE 的作用。

总损失中加入：

\[
L=L_{base}+\lambda_{sem}L_{sem}.
\]

## 10. 语义信息在 corrected-v4 专利主实验中怎样参与

专利主结果采用更容易隔离变量的“冻结 backbone 后分数级融合”。这里 DeepSeek、SBERT 和协同模型之间没有联合在线训练：每个 seed 先得到固定协同 checkpoint，再对同一 checkpoint 比较 baseline、real semantic 和 shuffled semantic。

### 10.1 构造用户语义画像

只使用用户在 train 中交互过的物品。设训练历史为 $I_u^{train}$：

\[
p_u=\operatorname{Normalize}\left(
\frac{1}{|I_u^{train}|}\sum_{i\in I_u^{train}}e_i
\right).
\]

这里 $e_i$ 就是原始文本或 DeepSeek 摘要经 SBERT 得到的物品向量。validation 和 OOD test 的正样本不会进入用户画像。

### 10.2 计算语义匹配分数

用户 $u$ 对候选物品 $i$ 的语义分数为：

\[
s_{sem}(u,i)=p_u^\top e_i.
\]

因为用户画像和物品向量都已归一化，该点积等价于余弦方向相似度。

### 10.3 与协同分数融合

协同分数和语义分数的尺度可能不同，代码对每个用户的全部候选物品分别做 z-score：

\[
s(u,i)=z_u(s_{cf}(u,i))+\alpha z_u(s_{sem}(u,i)).
\]

- `alpha=0`：只使用协同分数，即 baseline；
- `alpha>0`：加入语义匹配；
- `alpha` 仅在 validation 上选择，然后冻结；
- OOD test 不参与 `alpha` 选择。

MovieLens、Yelp 和 Food 使用统一 `alpha`；Amazon Beauty 还按照用户 train degree 划分低、中、高活跃组，使用验证集冻结的分组 `alpha`。

## 11. shuffled semantic 如何验证语义确实有用

项目构造了 `semantic_prior_shuffled.pt`：

- 保留全部 SBERT 向量；
- 保留向量维度、范数和总体数值分布；
- 仅随机置换物品行，使物品 ID 与语义向量错误对应；
- 记录的固定 `shuffle_seed=20260731`；
- real 与 shuffled 使用相同 checkpoint、相同 `alpha` 和相同评测过程。

因此 real 与 shuffled 的主要差别只有“语义是否属于正确物品”。如果 real 优于 shuffled，就能排除“只是增加随机向量通道也会提升”的解释。

v4 OOD NDCG@20 中：

| 数据集 | 语义文本来源 | baseline | real semantic | shuffled | real 相对 baseline | real 相对 shuffled |
|---|---|---:|---:|---:|---:|---:|
| MovieLens-1M | raw + SBERT | 0.06831 | 0.07037 | 0.06700 | +3.02% | +5.04% |
| Yelp2018 | DeepSeek + SBERT | 0.01345 | 0.01452 | 0.01314 | +8.00% | +10.52% |
| Food | DeepSeek + SBERT | 0.02780 | 0.02768 | 0.02661 | -0.42% | +4.03% |
| Amazon Beauty | raw + SBERT | 0.01824 | 0.03834 | 0.01466 | +110.24% | +161.56% |

KuaiRec v2 同样使用 DeepSeek+SBERT 先验，但 validation 最终选择 `alpha=0`，说明在当前曝光协议下，加入语义不能得到可确认增益。

## 12. 大模型有没有接触测试数据

没有。防泄漏链条如下：

1. DeepSeek 只处理 `metadata/items.jsonl` 中的物品静态文本；
2. SBERT 只编码上述物品文本；
3. 用户语义画像只聚合 train 交互物品；
4. checkpoint 和 `alpha` 只根据 validation NDCG@20 选择；
5. validation 选参脚本以 `load_test_gt=False` 运行；
6. confirmation 通过后才允许读取冻结的 OOD test；
7. 大模型从未接收测试用户、测试正样本或测试指标。

因此大模型提供的是外部物品内容知识，而不是把测试答案编码进模型。

## 13. 大模型没有参与哪些环节

DeepSeek 没有：

- 训练 LightGCN、CausalDiffRec 或扩散模型；
- 生成用户—物品交互；
- 选择随机种子；
- 选择 checkpoint、`alpha` 或活跃度分组权重；
- 直接输出推荐分数或 Top-K 列表；
- 读取 validation/OOD 标签；
- 在每个 epoch、每个用户或每次推理时被调用；
- 根据 OOD 结果修改摘要。

SBERT 也没有在推荐数据上微调。它只执行固定的本地文本编码。

## 14. 实验能否证明“DeepSeek 本身带来了提升”

**现在可以在 Yelp2018 上证明独立正向贡献，但不能概括为对所有数据集都有效。** 2026-09-05 新增了原始文本与 DeepSeek 优化文本的严格配对对照：

```text
原始文本 -> 同一 SBERT -> raw prior
DeepSeek 摘要 -> 同一 SBERT -> LLM prior
                         |
             同一冻结协同 checkpoint
             同一候选集、评价函数
             同一 validation 选定 alpha
```

对照中保持不变的因素包括：

- 推荐数据划分、训练交互和 OOD 候选物品；
- 每个 seed 的冻结协同 checkpoint；
- SBERT 模型 `sentence-transformers/all-MiniLM-L6-v2`；
- 384 维、L2 归一化、100% 物品覆盖率；
- 用户语义画像构造方式、按用户 z-score 标准化、Top-20 评价方式；
- `alpha` 候选集和选参/确认种子。

唯一有意改变是：SBERT 接收“原始拼接文本”还是“DeepSeek 规范化摘要”。主对比的共享 `alpha` 由 LLM prior 在 selection seeds `1024/2048/3072` 上选择，然后原样用于 raw prior；再在不相交的 confirmation seeds `4096/5120` 上确认。选参阶段显式设置 `load_test_gt=False`。

### 14.1 validation-only 门禁结果

| 数据集 | 共享 alpha | selection: LLM / raw | confirmation: LLM / raw | 门禁 |
|---|---:|---:|---:|---|
| Food | 0.25 | 0.031600 / 0.030126 | 0.031204 / 0.029905 | 通过 |
| Yelp2018 | 0.25 | 0.051961 / 0.050997 | 0.051505 / 0.050307 | 通过 |
| KuaiRec v2 | 0 | 0.460596 / 0.460596 | 0.464076 / 0.464076 | 未通过，不读取 OOD test |

KuaiRec 上两类 prior 的最优融合权重均为 0，所以根据预定规则停止，没有为这项新消融读取 KuaiRec OOD 标签。

### 14.2 冻结后的一次性 OOD 结果

| 数据集 | 协同 baseline NDCG@20 | raw+SBERT | DeepSeek+SBERT | DeepSeek - raw | 相对 raw | DeepSeek 胜出 seeds |
|---|---:|---:|---:|---:|---:|---:|
| Yelp2018 | 0.013448 | 0.013630 | **0.014524** | **+0.000894** | **+6.56%** | **5/5** |
| Food | 0.027800 | **0.027946** | 0.027684 | -0.000262 | -0.94% | 1/5 |

Yelp2018 上，DeepSeek - raw 的五种子配对差描述性 95% t 区间为 `[0.000403, 0.001385]`，单侧精确符号检验 `p=0.03125`。这组结果支持：在 Yelp2018 的实验条件下，DeepSeek 对异构原始文本的规范化改写，比直接将原文输入同一 SBERT 得到更好的 OOD 推荐结果。

为避免共享 alpha 可能偏向 DeepSeek 路径，还做了“同等调参预算、两类文本各自使用 validation 最优 alpha”的辅助对照。Yelp2018 中 raw 自选 `alpha=0.15`，DeepSeek 自选 `alpha=0.25`；OOD NDCG@20 分别为 0.013530 和 0.014524，DeepSeek 绝对提升 0.000994、相对提升 7.35%，5/5 种子胜出，配对差描述性 95% t 区间为 `[0.000457, 0.001531]`，单侧精确符号检验 `p=0.03125`。因此，Yelp2018 的正向结论在“严格共享权重”和“各自同等选参”两种口径下都成立。

Food 在 validation 上通过，但 OOD 方向反转，因此必须作为负结果/适用边界保留。它说明不能声称 DeepSeek 改写对任意数据集必然有效。

因此，专利可以写：

> 在 Yelp2018 实施例中，在保持协同检查点、语义编码器和融合权重相同的条件下，将 DeepSeek 规范化摘要编码为语义先验，相对直接编码原始文本的 OOD NDCG@20 提升 6.56%，五个配对随机种子方向一致。

不能把 MovieLens 或 Amazon 的提升归功于 DeepSeek，因为这两个数据集的终版先验是 raw+SBERT。也不能写“DeepSeek 摘要在所有数据集必然提升准确率”。

## 15. 专利中推荐怎样描述大模型角色

推荐表述：

> 获取物品的标题、类别、描述和属性信息；按照物品标识对所述信息进行对齐；可选地，将所述信息输入预训练大语言模型，由所述大语言模型生成保留物品类别、关键属性及使用意图的规范化语义描述；将所述规范化语义描述或原始物品文本输入预训练语义编码模型，得到与物品一一对应的语义向量；基于用户在训练期交互过的物品语义向量构造用户语义画像，并将用户—物品语义匹配分数与协同推荐分数进行标准化融合。

“可选地”很重要，因为正式正向数据中既有 DeepSeek+SBERT，也有 raw+SBERT。这样写既覆盖实际实现，也不会夸大 DeepSeek 的独立实验贡献。

不推荐表述：

- “大模型直接预测用户下一次点击”；实际没有这样做。
- “所有物品语义均由 DeepSeek 生成”；MovieLens 和 Amazon 不是。
- “DeepSeek 读取用户历史生成个性化推荐”；DeepSeek 没有读取用户历史。
- “实验已经证明 DeepSeek 在所有数据集都比原始文本更好”；严格配对消融仅在 Yelp2018 上得到正向 OOD 证据，Food 为负向，KuaiRec 未通过门禁。
- “训练和线上推理依赖 DeepSeek API”；实际只在离线预处理阶段调用一次并缓存。

## 16. 可复现步骤

### 16.1 DeepSeek 摘要 + SBERT

以 Food 为例：

```bash
export DEEPSEEK_API_KEY=<密钥只放环境变量>
python scripts/build_semantic_prior.py \
  -d food \
  --mode llm \
  --backend sbert \
  --sbert_model sentence-transformers/all-MiniLM-L6-v2 \
  --batch_size 64
```

Yelp2018 和 KuaiRec v1 只需替换 `-d`。建议显式写 `--mode llm --backend sbert`；不要依赖 `auto`，因为 `auto` 会根据 API key 和本地依赖是否存在而改变实际路径。

### 16.2 原始文本 + SBERT

MovieLens 或 Amazon Beauty：

```bash
python scripts/build_semantic_prior.py \
  -d movielens1m \
  --mode raw \
  --backend sbert \
  --sbert_model sentence-transformers/all-MiniLM-L6-v2 \
  --batch_size 64
```

### 16.3 corrected-v3 E3 载入先验

```bash
python train_lsci.py -d food \
  --data_root data_strict/processed/food/v1_strict \
  --use_semantic_prior \
  --semantic_prior_path \
    data_strict/processed/food/v1_strict/features/semantic_prior.pt \
  --lambda_sem 0.1
```

### 16.4 corrected-v4 主实验

先运行 validation-only 脚本选择 `alpha`，再由冻结 OOD 评测脚本读取同一 prior。关键脚本为：

- `scripts/validate_late_fusion.py`；
- `scripts/evaluate_late_fusion.py`；
- `scripts/validate_activity_adaptive_fusion.py`；
- `scripts/evaluate_activity_adaptive_fusion.py`。

### 16.5 原文与 DeepSeek 文本来源配对消融

```bash
bash scripts/run_raw_sbert_prior_build.sh
bash scripts/run_text_source_validation.sh
bash scripts/run_text_source_ood.sh food \
  data_strict/processed/food/v1_strict \
  experiments/reports/food_v5_raw_vs_deepseek_validation.json 0
bash scripts/run_text_source_ood.sh yelp2018 \
  data_strict/processed/yelp2018/v1_strict \
  experiments/reports/yelp2018_v5_raw_vs_deepseek_validation.json 0
```

`run_text_source_ood.sh` 会先读取 validation 报告中的 `ood_test_allowed`；门禁为 false 时直接停止，不读取测试真值。

## 18. 一句话总结

大模型在本项目中承担的是**离线物品文本规范化**：DeepSeek 将部分数据集的异构元数据压缩成语义摘要，SBERT 将摘要或原始文本变成固定的 384 维物品先验；推荐系统随后只使用本地向量，通过端到端条件融合或冻结 checkpoint 后的分数融合参与实验。严格的 raw-vs-DeepSeek 配对消融已证明 DeepSeek 改写在 Yelp2018 上带来 6.56% 的 OOD NDCG@20 相对提升（共享 alpha）；在两类文本各自获得同等 validation 调参预算时，相对提升为 7.35%。但 Food 为负向、KuaiRec 未通过门禁，因此该贡献应限定为特定数据与实施条件下的实验结论。
